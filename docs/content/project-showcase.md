# 页面二项目展示内容基线

> 目标岗位：AI 全栈开发工程师（AI Agent 方向）。页面优先服务招聘方快速判断，不按开发日志顺序堆砌技术名词。

## 1. 信息策略

面试官通常先判断四件事：候选人解决了什么问题、是否真正做过、Agent 是否受控可靠、能否把前后端和上线链路打通。因此页面采用两层阅读：首屏 15 秒扫读结论；展开后看架构决策、验证证据和诚实边界。

两个项目形成互补：

- **AI 面试协作站**：产品感、RAG 数字分身、预约事务、可靠通知和完整交付流程。
- **Sleep AIoT Agent 平台**：Agent 编排/评测/安全护栏，以及云端、数据面、客户端和边缘设备的纵向能力。

## 2. 项目一：AI 面试协作站

### 首屏摘要

**把“看简历、追问项目、约面试”合成一个可验证的 AI 产品。**

面试官可以边浏览简历与项目边向数字分身追问，并在同一站点完成登录、选时段、二次确认、改期和取消。大模型只负责基于资料回答问题，预约始终走确定性 UI 与后端事务，不把业务写权限交给 Agent。

### 我的工作

- 从 PRD、SRS、领域模型、UI、架构、安全、接口到测试计划建立可追溯设计链。
- 设计 RAG + L1 Persona：事实由知识库约束，人格只改变表达；无证据拒答，Prompt Injection 不得改变系统规则。
- 设计预约一致性：Slot 行锁、唯一索引、统一锁顺序、原子改期/取消与同事务 Outbox。
- 设计通知可靠性：候选人与面试官多投递目的、独立通道重试、死信、退信、人工重发和至少一次语义。
- 设计 SSE 恢复：从已提交 PostgreSQL 状态派生，先订阅后快照，漏序/断线强制重拉。

### 值得深挖的决策

1. 为什么 Agent 不自动预约：招聘场景需要可解释、可撤销、可审计，确定性事务比模型自主调用更可靠。
2. 为什么 SSE 不把 Redis Pub/Sub 当真相源：它不可持久化/重放，DB commit 与 publish 会形成双写丢事件窗口。
3. 为什么通知事件与投递目的分离：同一预约事件需要同时通知候选人与面试官，事件表达业务事实，delivery_purpose 表达投递意图。
4. 为什么手动重发新建尝试：保留每次外部投递的独立状态、退信和审计证据。

### 页面证据区

开发完成前显示：**设计基线已批准，正在实现与验证**。不得展示虚构接口数、测试通过数或线上流量。

开发完成后由实现真相更新：实际技术栈、通过的测试数量、RAG 评测结果、部署地址和可演示流程。更新必须来自源码/测试/部署证据，不从本文设计反推。

### 推荐追问

- “为什么预约改期要统一锁新旧 Slot？”
- “RAG 找不到证据时怎么避免编造？”
- “外部邮件已发送但数据库回执失败，如何处理重复？”
- “如何保证 Agent 永远不能绕过预约 UI？”

## 3. 项目二：Sleep AIoT Agent 平台

### 首屏摘要

**把睡眠健康场景做成受治理的 Agent 系统，而不是给聊天框接一个模型。**

系统贯通 React/Taro 客户端、NestJS 控制面、Python Agent 服务、RAG、MQTT/流处理和 ESP32-S3 边缘源码；高影响工具必须经过策略检查和人工审批，模型不可凭输出直接执行设备写操作。

### 我的工作

- 基于 LangGraph 构建 `route → policy → finalize` 运行图，并支持 local/Temporal 双协调模式。
- 设计 Function Calling 工具分级：读工具按最小权限执行，设备写工具进入 deterministic plan、HITL 审批和执行期二次校验。
- 构建 pgvector RAG 与 response guard：检索引用不可被模型替换，无证据时返回 `grounded=false` 而不是编造。
- 打通 NestJS、FastAPI Agent、PostgreSQL/TimescaleDB、Redis、MQTT、Kafka/Flink/ClickHouse 与 Taro/React 客户端的工程边界。
- 建立 Agent 评测、Prompt Injection、隐私隔离、发布门禁和可观测证据。

### 可复核证据

- Agent 工程回归：**84/84**，任务成功率 100%、工具选择准确率 100%、审批绕过率 0%。
- 语义/RAG 评测：**8/8**；Agent 单元测试：**54/54**。
- Prompt Injection：**10 例攻击，0 次越权写操作**。
- 控制面规模：NestJS **145 个 TypeScript 文件、22,968 行、115 个 REST 端点、35 张数据表、36 个测试文件**。
- 本地真实中间件证据：PostgreSQL/pgvector、Redis 双实例、EMQX 双客户端共享订阅；这些是本地验证，不是生产流量或云端高可用证明。

### 诚实边界

- 84 例是确定性软件回归基线，不等于外部大模型回答质量或真实用户成功率。
- 当前没有物理设备，固件和设备路径使用模拟遥测验证；不得声称真机、量产或硬件在环已通过。
- Kubernetes/Terraform/GitOps 资产已就绪并完成本地静态/协议验证，但真实阿里云 staging 尚未执行，不能写“已生产上线”。
- 项目工作树正在做最后上线调试，页面只读取证据，不改动该仓库。

### 推荐追问

- “为什么工具审批不能只靠 Prompt？”
- “LangGraph 与 Temporal 分别解决什么问题？”
- “RAG 引用如何防止被模型改写？”
