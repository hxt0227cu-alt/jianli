> 目标：把 jianli 站点（FastAPI + 预约 Worker + PostgreSQL + Redis + 前端）部署到候选服务器，完成域名 + HTTPS 的真实环境验收。

## 1. 服务器初始化

```bash
# 以 root 或 sudo 用户登录服务器后
sudo apt update && sudo apt upgrade -y
# 安装 Docker + Compose v2
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER   # 重新登录生效
# 备份/恢复依赖（PostgreSQL 16 服务应使用 16 或更新的客户端）
sudo apt install -y postgresql-client-16 openssl tar coreutils
docker --version && docker compose version && pg_dump --version && pg_restore --version
```

先在云安全组只放行实际 SSH 端口、TCP 80 和 443；PostgreSQL、Redis、Prometheus、Grafana
均不得开放公网。主机启用防火墙前先确认当前 SSH 端口，避免把自己锁在服务器外：

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH       # 若 SSH 不是 22，请改成实际端口
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose
sudo ss -lntp                # 公网监听只应有 SSH、80、443
```

## 2. 上传代码 + 配置环境

```bash
# 上传代码到服务器（任选：git clone / scp；以 git 为例）
git clone <your-repo-url> jianli && cd jianli

# 前端由 deploy/Dockerfile.nginx 在不可变 Web 镜像中按 pnpm lock 构建；
# 不上传本地 dist，也不要用 npm 临时解析依赖。

# 创建生产环境变量文件（服务器上执行，密钥只在这里）
cp apps/api/.env.prod.example .env
nano .env                        # 填入全部真实密钥（见第 0 节 P1）
chmod 600 .env                   # 权限收紧，防误读
```

> ⚠️ `.env` 在服务器上，**不要**提交进 git。部署预检会拒绝 `CHANGE_ME`、示例域名、弱密码、缺失变量以及非 `0600` 权限。
> `JIANLI_WEB_BASE_URL`、唯一的 `JIANLI_ALLOWED_ORIGINS` 与证书命令域名必须是同一个小写 DNS 名；脚本会在构建或签发前拒绝端口、路径、userinfo、query 或三者不一致。

## 4. 首次数据库迁移（生产库）

`scripts/deploy.sh` 会通过一次性 `migrate` 服务先执行 `alembic upgrade head`；
迁移失败时 Slot 物化、API 和 Worker 都不会启动；物化失败时 API 和 Worker
同样不会启动。不要再手工重复执行首次迁移。可用以下命令查看结果：

```bash
docker compose -f docker-compose.prod.yml logs migrate slots
```

`slots` 会按中国标准时间幂等生成滚动 8 周、每天 09:30–22:00 的 30 分钟格，
读取仓库内经官方通知核对的年度日历；不会覆盖 `booked` / `owner_locked`。
若部署窗口跨入尚未登记官方日历的年份，命令会失败关闭，必须先补该年度 JSON，
不得把未知节假日当普通工作日。

## 4.5 初始化 owner_admin 账号（管理员登录，必须）

> 生产库没有任何 owner_admin 账号可登录（开发 seed 的密码是占位符，**不可登录**）。
> 用 `scripts/create-owner.sh` 创建/重置管理员账号——密码**只走环境变量**，不写进 `.env` 或任何文件。

```bash
# 在服务器项目根目录执行（先替换邮箱与强密码；密码 ≥10 字符）
JIANLI_OWNER_EMAIL=你的管理员邮箱@example.com \
JIANLI_OWNER_PASSWORD='你的强密码' \
./scripts/create-owner.sh
# 期望输出：[OK] owner_admin 就绪：…（role=owner_admin, verified=true）
```

- 幂等：重复执行同一邮箱会**重置密码**（忘记密码时重跑一次即可）
- 之后用该邮箱+密码登录站点「知识库管理」入口（admin 页面）
- 部署验证清单第 6 节含对应检查项

## 4.6 初始化 canonical 知识库（20 篇，必须）

先完成 4.5 的真实管理员初始化，再执行一次性工具服务；它使用镜像内生产语料，
不会从 `tests/` 导入，并以 `appuser` 写入已初始化权限的知识卷：

```bash
docker compose --profile tools --env-file .env -f docker-compose.prod.yml run --rm seed-kb
# 期望：verified canonical corpus: 20/20 active + indexed
# 可重复执行；相同 checksum 会幂等跳过，再次验证仍为 20/20。
docker compose --env-file .env -f docker-compose.prod.yml exec -T api \
  sh -c 'test -w "$JIANLI_KNOWLEDGE_STORAGE_DIR"'
```

## 5. 域名 + HTTPS

```bash
# 确认 DNS 已解析到服务器后（第 0 节 P4）：
# 首次 deploy 使用不引用证书的 HTTP bootstrap 配置；它只开放 ACME challenge
# 与 /nginx-health，其他业务请求均返回 503，不能通过 IP 暂时公开网站。
# 申请成功后，脚本会原子生成 HTTPS 配置、nginx -t 并 reload：
JIANLI_ENV_FILE=$PWD/.env ./deploy/certbot-init.sh 你的域名 your-email@example.com
```

不要手工修改 `deploy/nginx.conf`。它是首次启动用的 HTTP 模板；正式 HTTPS
配置由 `deploy/nginx-https.conf.template` 原子渲染到 `deploy/runtime/default.conf`；
`nginx -t` 或 reload 失败会自动恢复旧配置，不得手工绕过校验。

验证：
```bash
curl -I https://你的域名        # 期望 200 + TLS
curl -I http://你的域名          # 期望 301 → https
```

### 7.1 隔离恢复演练（至少每月一次）

恢复脚本拒绝生产库同名目标、非空目标库，也拒绝已有目录、生产知识目录及其子目录。
先创建一个全新的空测试库，再显式提供隔离目标；不得把这些变量指向生产库或生产知识卷：

```bash
export JIANLI_RESTORE_CONFIRM=ISOLATED_RESTORE
export JIANLI_BACKUP_PASSPHRASE='<独立备份强口令>'
export JIANLI_RESTORE_DB_HOST=127.0.0.1 JIANLI_RESTORE_DB_PORT=55433
export JIANLI_RESTORE_DB_NAME=jianli_restore_$(date +%Y%m%d)
export JIANLI_RESTORE_DB_USER=jianli_restore JIANLI_RESTORE_DB_PASSWORD='<独立随机测试库密码>'
export JIANLI_RESTORE_ROOT=/srv/jianli-restore
export JIANLI_RESTORE_KNOWLEDGE_DIR=$JIANLI_RESTORE_ROOT/$(date +%Y%m%d)
./scripts/restore.sh backups/jianli-backup-<timestamp>.tar.gz.enc
```

`restore.sh` 先核验 SHA-256，再在 `0700` 临时目录解密；解包前会拒绝路径穿越、
链接和设备文件。恢复库必须使用区别于生产的角色与密码，且目标库必须已存在、为空；
`pg_restore` 使用单事务且不带 `--clean`，
因此不会主动清空既有库。完成后核对表/行数、20 篇 active/indexed 与文件数，记录 RTO；
演练结束只删除上述独立测试库和独立知识目录。

## 9. 已知限制与风险

- **备案周期**：内地地域服务器需 ICP 备案（1-2 周），期间域名不可正式对外；可先用 IP:端口验证功能
- **容量边界**：候选栈有 8 个常驻服务，容器内存上限合计约 3.1GiB，构建阶段还需要额外峰值；2C4G 只能做短时 smoke，不作为正式容量。单机候选至少 4C8G，并在压测后按 CPU、内存和 P95 决定是否继续升配。
- **正式拓扑尚未裁定**：approved architecture 要求托管 PostgreSQL 与对象存储；当前 Compose 的本机 PostgreSQL + `jianli_knowledge` named volume 仅是候选/staging 实现。正式上线前必须选择“回到 approved 腾讯云拓扑”或审批等价的阿里云 RDS/OSS 拓扑，并据此完成凭据、备份和恢复验收。
- **备份策略**：`backup.sh` 只保留加密包与校验文件（明文仅存在于退出即清理的 `0700` 临时目录）；异地备份仍需配置 OSS，否则服务器磁盘故障仍会丢数据
- **admin 问答审计实现已完成、生产执行待验收**：`conversation_messages` 的客观引用数/耗时/grounded 字段与可逆 0009 迁移已在开发真实库验收；正式环境仍须在备份后执行 `alembic upgrade head`，再用 owner_admin 验证列表与消息详情，不能把开发库证据冒充生产迁移结果。
- **首次镜像下载依赖公网**：服务器首次执行会拉取 Python、PostgreSQL、Redis、Nginx 与 Certbot 镜像；网络失败时停止部署并先修复服务器网络/镜像源，不要循环重试。
