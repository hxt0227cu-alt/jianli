访客进入站点 → ① 简历问答（了解"你是谁 / 做过什么"）→ ② 项目追问（深入技术决策与代价）→ ③ 面试预约（行动：选时段 → 确认函 → 日历同步）。三件套对应 **了解 → 深入 → 行动**。

## 01 背景与问题

（动机式叙事，非市场痛点）

我做的是「自己的求职展示困境」的解法：简历 PDF 是静态的，写不下技术深度；而通用 AI 问答会编造经历——在面试场景里，编造 = 诚信风险。

两个真痛点：
1. 简历 PDF 静态，技术深度无法展开。
2. 通用 AI 编造经历，在面试场景是不可接受的诚信风险。

边界条件（设计第一原则）：**真实性优先**——宁可不答，绝不编造；回答必须可溯源至简历 / 项目材料。

由此长出三件套：简历问答 / 项目追问 / 面试预约（了解 → 深入 → 行动）。

设计约束优先级：**真实性 > 稳定性 > 成本**。

北极星：简历事实一致率 ≥ 94%（SLO）。26 题同源事实锚点评测集已就绪（对齐 R1–R26，脚本 `scripts/measure_fact_consistency.py` 可复跑），**实测待跑**——最近一次跑 `scripts/fact_consistency_results.json`（2026-08-17）显示 26 题全 `503 Service Unavailable`，无任何一题真测出答案，故无真实数字；当前以 LITERAL 8/8 + REJECT 10/10 作为代理指标，SLO ≥ 94% 为达成目标。

## 02 架构与选型

（每条讲「放弃 → 代价 → 成果」，挑重点）

**主线一 · 后端：FastAPI 单体**
- 放弃：微服务 / 多服务拆分。
- 代价：单体内模块边界要靠纪律维护。
- 成果：部署简单、迁移可本地 PG 全可逆验证、一个人能扛。

**主线二 · 向量：PostgreSQL + pgvector**
- 放弃：独立向量库（Milvus 等）。
- 代价：PG 要换 pgvector 镜像、向量检索受 PG 能力约束。
- 成果：一套存储管业务数据 + 向量，运维面最小；知识库从静态页 → pgvector RAG 演进只引 4 个迁移。

**主线三 · 知识库：静态页内容 → 上传式 pgvector RAG**
- 放弃：一开始就把知识库做重。
- 代价：4 个迁移 + 引 pypdf / python-multipart + PG 换 pgvector 镜像。
- 成果：真实文档问答，能 dogfood 自己的简历。

**扩展性答法（规划，非已实现）**：语料增大后 pgvector 单表检索会到瓶颈，路线是分块表 + 只读副本 / 专门向量服务；当前规模未触发，不提前建。

**其他约束（一笔带过）**：前端 React SPA；LLM 走 Stub 兜底保证零外部依赖可跑；安全按加密 / 鉴权 / 审计落地；Agent 只做只读检索，不自动写预约。

## 03 Agent 与 RAG

（完整演进：「最初 → 问题 → 改 → 代价 → 成果」）

**① embedding：768 维本地哈希 → 1024 维 BGE-M3**
- 问题：本地哈希无语义，跨词改写召回差。
- 改：换硅基流动 BGE-M3（1024 维）。
- 代价：旧向量丢失需重灌 + 引硅基流动 API 依赖 + dimensions 配置。
- 成果：HIT 8/8 保持；纯向量 EXTREME avg-rank 1.8 → 1.3。

**② 检索：纯向量 → 混合（向量 + BM25 + RRF）**
- 问题：纯向量在小语料上对退化 / 改写鲁棒性差。
- 改：加 BM25（Okapi）+ RRF 融合 top6。
- 代价：分块 500/50 + bm25.py + RRF 实现。
- 成果：小语料 top-6 全召回，对退化鲁棒。

**③ 拒答：无阈值 → 双层门槛（kb_min_score=0.47 + CJK 停用词）**
- 问题：无阈值时什么都答，越界问题也编。
- 改：0.47 相关性阈值 + CJK 功能字停用（防单字重叠误判命中）。
- 代价：校准（边界仅差 0.001，一次失败重写）+ 调参。
- 成果：REJECT 10/10（100%）闭环。

**④ Agent：系统硬编码 tool_calls → 两阶段 function calling（模型自主 query）**
- 问题：硬编码检索词不灵活，遇新问法漏召。
- 改：注册 `search_knowledge` 白名单只读工具，模型自主决策检索词（决策链 SSE 可见）。
- 代价：3 轮调试 + greeting 整词修复（"hi"⊂"litchi" 误判根因）+ 复杂度上升。
- 成果：LITERAL 8/8 + REJECT 10/10 恢复；模型自主决策、决策链可见。

**Agent 安全**：模型仅能调用 `search_knowledge` 这一个只读白名单工具，产出查询字符串 → 固定混合检索（无 SQL 执行路径，无法跑 "SELECT * FROM users"）；无命中 → 拒答；引用按 chunk（doc + fragment）返回，不返全量。

**检索失败兜底（诚实）**：当前无命中统一走 offtopic，建议用户换种问法或转入面试预约；**不提供「转人工 / 留言」入口（产品决策：不实现**，避免引入未鉴权的外部接触面）。

**一段开发经历：评测如何把"看起来正常"变成"P1 缺陷"**

最早那版问答，越界问题一律硬召回、照答不误——比如问"你们公司营收多少"，它会硬从简历语料里凑一句答出来。当时没有拒答评测，系统对外表现"拒答率 0%"，看起来一切正常，我甚至一度觉得"召回率高挺好"。

直到我把 `REJECT 10/10` 这组越界题加进评测基线：10 道明显越界的问题，**预期全部拒答**。第一次跑，10 道全"答了"——拒答率 0% 瞬间从"优点"翻转成"P1 缺陷"：它根本分不清"该答"和"不该答"。

定位很快：检索没有相关性兜底，任何 query 都能在 0.001 以上的相关度里命中。于是我加了 `kb_min_score=0.47` 双层门槛（相关性阈值 + CJK 停用词防单字重叠误判），校准时因为边界只差 0.001 重写过一次。再跑 `REJECT`：10/10 全拒。

这段经历让我确信的不是"阈值修好了"，而是**评测的滞后暴露能力**——如果没把"拒答率"变成可量化基线，那个 P1 会一直藏在"拒答率 0%"的好看数字里，直到真有人在面试里问了个越界问题、系统编了句假话才被察觉。坑是评测抓出来的，不是用户抓出来的；这恰恰证明这套评测体系在真正干活。
