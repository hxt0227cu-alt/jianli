## 1. 项目背景

### 1.1 现状描述
用户希望搭建一个对外可访问的**个人网站**，面向招聘方 / HR / 面试官。核心差异点：内置一个**基于自有知识库的大模型问答数字分身**（形态类比豆包 / 企业智能客服），并能在对话与专属页面中直接完成面试预约，且预约状态实时可见。

### 1.2 痛点列表
- 简历篇幅有限，能写的内容太少，面试官想深挖履历 / 项目细节时无从下手；
- 简历信息分散、不连贯，面试官难以按需快速了解候选人；
- 约面试依赖邮件 / 聊天工具来回沟通，效率低、易遗漏，且预约信息散落难追踪；
- 面试官若想修改已约时间 / 会议号，无账号体系无法路由回自己的预约，无法修改；
- 用户（候选人）希望在自己常用的工具里直接收到提醒并看到完整面试表，而不必在网站内再做一套带权限管理的后台。

### 1.3 引入方案简述（三大页面 + 数字分身 + 预约闭环）
构建一个「个人站点 + 自建云端问答数字分身 + 面试预约系统」的混合型产品，主体为三个页面：

- **页面 1 · 首页 / 简历问答页**：左栏渲染简历（按模块拆块），右栏为大模型问答窗口，面试官边看简历边提问；页内含**推荐问题 / 示例问答版块**（不知问什么时一键提问）；**页面文字可选中复制**，方便面试官复制内容后向大模型提问；**左下角放置"下载简历（PDF）"按钮**；提问告一段落可经"预约面试"入口进入页面 3。
- **页面 2 · 个人项目展示页**：以 **HTML 网页版 + 动效**形式展示项目，增强互动感；页面**右侧同样保留大模型问答窗口**，面试官浏览项目时可即时向"数字分身"提问项目细节；**页面文字同样可选中复制**。
- **页面 3 · 动态面试表页**：交互式课程表。空闲时段格子为**绿色**、已预约为**红色**；面试官**登录后**点击绿色格子填写表单（公司名称 / 会议平台 / 会议号 / HR 联系方式 / **备注**）提交，格子由绿转红，所填信息**加密隐藏**；本人可修改自己填过的红色格子或取消后重约；**一家公司仅能预约一个时段**（重复预约系统提醒）；候选人（用户）**日常在飞书多维表格中查看含全部公司的完整面试表**；**飞书不可用时，可在网站 admin 后台通过只读应急视图查看完整预约**（不可改/删），并**经飞书 + 邮箱收到预约 / 修改 / 取消等提醒**（微信 WorkBuddy 助理为延后项）。

- 问答数字分身：在 RAG 事实作答之上叠加用户专属人格（第一人称、本人风格 / 情商 / 逻辑），越界以本人口吻拒答、不编造事实。
- 问答**对外公开、无需登录**；但页面 3 的预约 / 修改 / 取消操作**需面试官登录**（角色认证 + 免登录复访）。
- 云端部署（本机不搭服务器）；**桌面端优先，不做移动端适配**。

## 2. 需求目标

- **R1【核心】** 三大页面：① 简历问答页（左简历 / 右问答 / 推荐问题 / 文字可复制 / 简历下载按钮）；② 项目展示页（HTML 动效 + 右问答 / 文字可复制）；③ 动态面试表页（需登录）。
- **R2【核心】** 自建并云端部署的知识库问答：基于 PDF / 文档 / MD 作答，越界明确拒答；大语言模型通过第三方托管 API 调用。**MVP 仅使用 DeepSeek 单模型**；混元 Fallback 为规划中的冗余能力，**延后实施**（见 §8.13 MVP 范围；推理方案见 `docs/references/agent-engineering-frameworks.md`）。
- **R3** 多页问答窗口：页面 1 左简历右问答；页面 2 右侧问答；形态类比京东 / 美团智能客服，公开可问。
- **R4** 推荐问题 / 示例问答版块：基于知识库索引**异步生成并缓存**可点击推荐问题（页面读取缓存，缺失走固定兜底问题）；页面 1、页面 2 各一套。
- **R5** 简单管理后台（候选人 admin）：登录后上传知识库、查看对话、管理不可约时段与页面公告。
- **R6** 纯中文界面；总体简洁清爽（参考豆包）；页面 2 项目展示需有动效、互动感强；**桌面端优先，不做移动端适配**。
- **R7【核心】** 人格层（数字分身）：**路径=L1（persona 提示词 + few-shot 风格样本）**——最简单、最稳、零训练成本，MVP 即用；L2 LoRA 微调已规划（语料收集中，见 `docs/experiments/deferred/l2-persona-training.md`），L3 作可选增强。**第一人称、本人风格 / 情商 / 逻辑；越界仍本人口吻拒答、不编造**。
- **R8【核心】** 动态面试表页（交互）：课程表式，绿=空闲 / 红=已约 / 黄=选中待确认；点击绿格填表预约、绿转红；信息加密隐藏；实时刷新。
- **R9【核心】** 面试官登录注册：账号体系（独立于候选人 admin）用于预约、修改、取消与"一家公司一时段"限制；支持**记住我（有效期 14 天）**免登录复访。
- **R10【核心】** 提交预约：填写 公司名称 / 会议平台 / 会议号 / HR 联系方式（电话 + **姓氏 + 敬称**）/ **备注（选填）**；提交后信息加密存储、网站端不展示明文；格子绿转红；实时刷新。
- **R26【核心，v2.1 新增】** 预约信息二次确认 + 确认函回执：面试官填完表单后**不直接落库**，先弹出**信息确认表**核对三要素（公司名称 / 收件邮箱 / 称呼）；确认无误后才执行原子落库，并**以候选人本人邮箱为发件人**向面试官注册邮箱发送一封**预约确认函**（模板见 §4.5.1）。收件邮箱固定为注册时已验证邮箱、**不可编辑**；确认页限时 **3 分钟**，期间**不预占时段**，最终提交仍走原子锁校验。
- **R11** 预约修改 / 取消：仅本人可改自己填过的红色格子信息，或取消原预约后重约；**改会议号=原地改字段**（不涉及时段占用，直接更新）；**改时间=原子事务**：在同一数据库事务内先锁新段、占用新段、再释放旧段，新段不可用时原预约保持不变（**禁止"先释放原格再重选"**，避免并发下同时丢失新旧时段）。
- **R12** 一家公司一个时段（唯一约束公式，P1-6）：有效预约唯一约束 = 归一化公司名 与 账号 取**并集拦截**——同一归一化公司名仅一个有效预约 **且** 同一账号仅一个有效预约（任一命中即拦截）。归一化 = 去空格 / 统一小写 / 去常见标点后缀；候选人可在后台**手工解除异常拦截**（如集团不同事业部）。重复预约返回 `DUP_COMPANY` 或 `DUP_ACCOUNT` 并提醒。
- **R13** 候选人提醒（**MVP：邮箱 + 飞书双通道**）：新预约、修改（含改时间）、取消事件实时推送至候选人**飞书 + 邮箱**；面试前 **10 分钟**临近提醒同样经此双通道推送。**微信（WorkBuddy 微信助理）为延后项**，不在 MVP 范围（见 §8.13）。
- **R14** 飞书多维表格完整视图（候选人，**日常视图**）：系统将完整面试表（含全部有意向公司信息）同步至飞书多维表格，候选人在飞书**日常查看**完整信息（明文）。
- **R14a** 候选人后台只读应急视图（方案 B，P0-4）：飞书不可用时，候选人在 admin 后台可**只读**查看完整预约列表（全公司明文），仅查看与同步状态/故障记录，**不可修改/删除预约**；数据同源系统 DB，解密仅在飞书视图与后台应急视图发生。
- **R14b** owner 强制取消（受审计特殊操作）：owner 在后台**锁定已预约时段**（输入取消原因）触发系统**原子取消**该预约——释放占用 3 格（变 `owner_locked`）、向该面试官**注册邮箱**发送取消告知函（主题标注「（已取消）」，正文含原时段与「请重新预约」）、写 AuditLog（特殊审计）；**后台不提供直接修改/删除预约入口**，不称"三通道通知面试官"（见 §4.6 通知体系说明）。
- **R15** 简历 PDF 下载：页面 1 左下角按钮下载 PDF 简历。
- **R16** 隐私与安全：其他面试官不能查看红色格子内的任何可识别信息（仅显"已预约"）；所填表单加密存储，解密仅在**飞书日常视图**与**后台只读应急视图**发生，网站对外端不解密展示；本人（归属人）登录后可见自己填的明文并可改/取消。
- **R17** 候选人主动标记不可约时段 + 页面顶部公告：owner 可将任意格标红（不可约）；页面 3 顶部常驻可编辑公告，告知 HR「候选人临时有事会主动通过预留联系方式沟通」。
- **R18** 面试前临近提醒：面试开始前 **10 分钟**，向候选人推送飞书 + 邮箱提醒（MVP 双通道；微信延后）。
- **R19** 认证会话持久化（P2-1）：面试官 / owner 勾选「记住我」后，**认证会话**复访网站 **14 天**内免登录（属认证登录态，非问答历史）。
- **R20** 注册安全与合规：注册邮箱验证、密码找回、防刷（注册 / 登录 / 预约 / 问答限频，已确认阈值见 §5）、隐私说明（文案见 §8.6）。
- **R21** 飞书同步失败告警：飞书同步失败时有邮件告警与重试（微信通道为延后项，不在 MVP 同步范围）。
- **R22** 知识库来源：包含简历、项目资料（候选人将提供项目 MD 文件）等。
- **R23** 会话历史持久化：面试官登录后产生的问答会话**跨登录保留**，下次登录仍可看到原对话（类比豆包历史会话）；未登录时的会话为临时会话、不持久化。
- **R24** 知识库热更新：候选人在后台新增 / 删除 / 修改文档后，按「热更新分档 SLA」（功能表「热更新 SLA（P1-2）」行，按文件类型拆分）重新索引生效，后续问答立即反映最新内容，无需重新部署。**具体指标不在此重复**，以功能表为准。
- **R25** 页面文字可复制：页面 1、页面 2 的简历 / 项目正文文字可选中复制，便于面试官复制到问答框提问。

## 3. 业务场景

### 场景 1：面试官浏览首页并针对简历深挖（页面 1）
- 描述：面试官进入页面 1，左栏看拆块简历（文字可复制），右栏问答窗口针对简历细节提问；或点击推荐问题一键提问。
- 系统处理：检索知识库（简历拆块索引）→ 结合人格层第一人称作答 → 流式返回；若已登录，会话持久化（R23）。
- 关系：越界走场景 2；提问告一段落可经"预约面试"入口进入场景 6。

### 场景 2：越界问题被拒
- 描述：提问与"我"（资料 / 知识库）无关。
- 系统处理：识别越界 → 仍以本人口吻礼貌拒答并引导回正题，不编造事实。

### 场景 3：面试官浏览项目展示页并提问（页面 2）
- 描述：面试官进入页面 2（HTML 动效，文字可复制），浏览项目卡片，右侧问答窗口针对某项目细节提问。
- 系统处理：检索项目相关知识库（含项目 MD）→ 人格层作答 → 流式返回；可点击推荐问题。

### 场景 4：简历 / 项目 PDF 下载
- 描述：面试官在页面 1 左下角点击"下载简历"，获取 PDF 简历。

### 场景 5：推荐问题引导（示例问答）
- 描述：面试官不知从何问起，页面 1 / 页面 2 展示**知识库索引完成后异步生成并缓存**的推荐问题（缓存缺失时展示固定兜底问题），点击即提问。

### 场景 6：面试官登录 / 注册（进入页面 3 前置）
- 描述：面试官欲预约，进入页面 3 被要求登录；无账号则注册（邮箱验证）；支持「记住我」14 天免登录复访。
- 系统处理：校验账号 → 建立会话（面试官网与 admin 账号隔离）；注册需邮箱验证、密码找回、防刷限频（§5）。

### 场景 7：查看动态面试表（页面 3，登录后）
- 描述：面试官登录后看到课程表式表格，绿=空闲、红=已约、黄=选中待确认；红色格子对其他面试官仅显"已预约"（无公司名）；页面顶部有 owner 公告。
- 系统处理：读取系统内预约列表与不可约约束 → 渲染绿 / 红；建立 SSE 推送通道实时刷新。

### 场景 8：选择时段并填表预约（1.5h 选段 + 冲突校验 + 绿转红 + 加密）
- 描述：面试官点击绿色空闲格 → 自动高亮该格 + 同列后续 2 格（共 1.5h）为黄（待确认）；若高亮块触及红格则持续悬浮「不可选当前时间段」；无冲突则弹出表单（公司名称 / 会议平台 / 会议号 / HR 联系方式（电话+姓氏+敬称）/ **备注**）→ 点「下一步」→ **弹出信息确认表核对三要素（公司名称 / 收件邮箱 / 称呼）** → 确认并提交。
- 系统处理：确认页限时 3 分钟且**不预占时段** → 确认提交后校验"一家公司一时段"（场景 9，归一化公司名 + 账号并集比较）→ 服务端原子锁（抢占式，先提交者得；被抢占返回 `SLOT_TAKEN`）→ 写入预约（信息加密）→ 3 格转红 → SSE 实时刷新 → 事务成功后触发候选人双通道提醒（场景 11，MVP：飞书+邮箱）+ 飞书同步（场景 10）+ **向面试官注册邮箱发送预约确认函（场景 18）**；表单末附固定提示文案（见 §4.5）。
- 并发：两人同时点同一绿格 → 先提交者成功、后提交者收「该时段已被预约」并经 SSE 刷新为红（可选增强：编辑中「有人在编辑」气泡，参考 WPS 协作表）。

### 场景 9：一家公司重复预约提醒
- 描述：该公司名称（**归一化比较**，去空格/小写/去标点后缀）或该账号已有一个有效预约，再次提交。
- 系统处理：拦截并提示"一家公司仅可约一个时段"，不写入。

### 场景 10：候选人（用户）在飞书查看完整面试表
- 描述：用户在飞书多维表格查看含全部公司的完整面试表（明文：公司、会议平台、会议号、HR 联系方式、备注、时段、状态）。
- 系统处理：系统 DB 为唯一真相源，预约变更实时 / 近实时同步至飞书多维表格；同步失败邮件告警候选人 + 飞书任务重试（R21）。

### 场景 11：候选人预约提醒（双通道，MVP）
- 描述：新预约 / 修改（含改时间）/ 取消事件触发，候选人经**飞书 + 邮箱**收到提醒（**MVP 双通道**；微信 WorkBuddy 助理为延后项）。
- 系统处理：事件 → 飞书机器人 + 邮件 → 候选人；任一通道失败不影响其余，失败通道独立重试 + 告警，不相互兜底。

### 场景 12：修改 / 取消本人预约（原子化，P0-3）
- 描述：面试官登录后，仅能修改自己填过的红色格子（**改会议号原地改字段**；**改时间走原子事务：锁新段→事务内更新→占新段→释旧段→提交→通知**，新段不可用则原预约不变），或取消预约。
- 系统处理：校验归属（仅本人）→ 原子事务更新/释放 → 事务成功后才 SSE 实时刷新 + 双通道提醒（含变更说明，MVP：飞书+邮箱）+ 飞书同步；新段被占则保持原预约并提示重选。

### 场景 13：候选人标记不可约时段 / 编辑公告（owner 后台）
- 描述：候选人在 admin 后台将任意格标红（不可约），并编辑页面 3 顶部公告（告知 HR 临时有事会主动联系）。
- 系统处理：写入不可约约束 → SSE 实时刷新网格（红格）；公告持久化并在页面 3 顶部展示。

### 场景 14：面试前临近提醒（候选人，双通道）
- 描述：面试开始前 **10 分钟**，向候选人推送飞书 + 邮箱提醒（MVP 双通道；微信延后）。
- 系统处理：定时任务扫描临近面试 → 飞书 + 邮件推送。

### 场景 15：查看历史会话（面试官，登录后）
- 描述：面试官登录后，在问答界面可见自己过往的对话会话列表，点击可继续或回看（类比豆包）。
- 系统处理：会话按账号持久化（R23）；未登录会话不保存。

### 场景 16：知识库热更新（候选人 admin）
- 描述：候选人在后台新增 / 删除 / 修改知识库文档，系统近实时重新索引。
- 系统处理：变更触发增量嵌入 + 向量库更新（具体指标见功能表「热更新 SLA（P1-2）」行，按文件类型拆分）→ 后续问答即时反映最新内容，无需重新部署。

### 场景 17：管理员后台（候选人 admin，只读应急视图，P0-4）
- 描述：候选人登录后台上传 PDF / 文档 / 项目 MD 入库；浏览历史对话；并拥有**只读的完整预约应急视图**（飞书不可用或日常飞书查看的补充）。
- 权限边界（方案 B）：飞书为**日常完整视图**；网站后台保留**只读应急完整视图**（不可改/删预约，仅查看 + 同步状态/故障记录），明文仅在此时渲染，不做独立写操作。

### 场景 18：预约信息二次确认与确认函回执（R26，v2.1 新增）
- 描述：面试官填完预约表单后，系统弹出**信息确认表**，突出核对三要素——公司名称、收件邮箱（只读，取注册验证邮箱）、称呼（姓氏 + 敬称）。面试官可「返回修改」公司名与称呼；核对无误点「确认并提交」。
- 系统处理：确认页限时 3 分钟（超时 `CONFIRM_EXPIRED`，需重选时段）且**不预占时段**；确认提交后走原子锁落库（被抢占返回 `SLOT_TAKEN`）；事务成功后，**以候选人本人邮箱为发件人**向面试官注册邮箱投递预约确认函（模板见 §4.5.1），纳入 Outbox 幂等重试。
- 异常分支：确认函发送失败**不回滚预约**，记失败状态 + 飞书告警候选人 + 后台高优先级告警 + 可手动重发（`CONFIRM_MAIL_FAIL`）。
- 后续联动：改期成功重发确认函（时间更新）；会议平台 / 会议号变化重发更新确认函（含最新平台与会议号，与 §4.5.1 同步）；取消成功发送取消告知函（必须）。

| 知识库热更新 | 增 / 删 / 改文档后近实时重新索引生效，分档 SLA 见「热更新 SLA（P1-2）」行（R24） | 核心 |
| RAG 质量标准（P1-4） | ① 检索不到内容：明确告知"资料未涵盖"，**不编造**；② 多份资料冲突：以最新/权威源为准（来源优先级可配置）；③ 可展示引用来源（可选开关）；④ 含指令性文本触发 **Prompt Injection 防护**，不执行外部指令；⑤ 知识库删除后相关缓存答案失效；⑥ 允许基于已知事实的**合理推断**但须标注"推测"；⑦ 事实回答须基于知识库，人格层仅影响口吻，不改变事实 | 核心 |
| 热更新边界（P1-8） | 单文件 ≤10MB、单次 ≤20 文件；支持 文本型 PDF（直接解析文本）/ 扫描型 PDF（OCR）/ MD / DOCX / TXT；按页判断是否需要 OCR，避免对文本型 PDF 误跑 OCR 增加成本与错误；更新时**旧索引继续服务至新索引就绪**；更新失败回滚；删除文档**立即禁止被检索**；相同文件重复上传去重 | 核心 |
| 热更新 SLA（P1-2，按文件类型拆分） | ① 纯文本类（MD/TXT/DOCX/可复制文本型 PDF）：P95 ≤ 60s 生效；② 扫描 / 不可复制 PDF（需解析、非 OCR）：P95 ≤ 120s 生效；③ 扫描型 PDF（需 OCR）：异步处理，目标 P95 ≤ 5 分钟；删除文档：立即写入检索黑名单，P95 ≤ 5s 禁止继续命中；OCR 失败：旧索引继续服务并显示失败原因 | 核心 |

> 模型方案：按 **RAG** 落地（务实）；"训练自己的模型"先以 RAG + 人格提示词（**L1**）实现，微调（L2 已规划语料收集，L3 作可选）作增强。**问答基座用托管 LLM API（MVP 仅 DeepSeek，混元 Fallback 延后启用）**，无需自租 GPU，最稳最省；自训权重（L2/L3）仅在确有需要时进行。候选人将提供项目 MD 文件作为知识库来源之一。

### 4.5 动态面试表页（交互 + 预约）★ 精确规则
**网格布局**：课程表式。7 列 = 周一..周日；行 = 30 分钟时段，起始标签 9:30, 10:00, …, 21:30（最后一格 21:30–22:00），共 25 行。

**日历与时间规则（P0-2 / P2-2）**
- **系统时区**：中国标准时间（UTC+8）；所有时段以 `start_at` / `end_at` 时间戳（含日期与时分，如 `2026-08-10T09:30:00+08:00`）存储，不依赖"星期 + 格子编号"表达。
- **展示窗口**：默认展示**本周 + 下周两个完整自然周**（固定 14 天窗口）；本周中「今天之前」的日期置灰不可选（仅作历史占位，不渲染为可约格）；通过左右翻页箭头在「本周 / 下周 / 再下周…」间切换。按完整自然周分页，避免「连续 14 天横跨三周」与七列课程表错位（P1-1）。
- **不可预约当天**：仅允许预约"明天及以后"的时段；当天时段对预约不可选（仅展示状态）。
- **最短提前量（统一规则）**：预约截止时间为面试日期前一自然日 **22:00（UTC+8）**；开场前不足该截止时间的时段不可选。**不再使用"至少提前一天"表述**（二者不等价：前一日 21:30 预约次日 20:00 仅提前 22.5h，但按 22:00 截止规则仍允许）。
- **翻页规则**：左箭头显示上一周、右箭头显示下一周；早于当日或晚于窗口的边界不可翻。
- **休息日规则（拆分三类，避免周末与法定节假日混淆）**：
  - ① 周末：周六、周日全天红（不可约）；
  - ② 法定节假日：按**官方发布的年度法定节假日表**自动标红（不可约）；
  - ③ 调休工作日：因调休而上班的周末，**可约**（按普通工作日处理，不标红）；
  - ④ owner 人工覆盖：owner 可在节假日 / 调休上手动增删红格，人工覆盖优先级高于自动规则。
- **节假日来源与优先级**：数据源 = 国务院/官方发布的年度节假日安排（静态配置 + 每年更新）；自动规则 < owner 人工覆盖。
- **每时段以时间戳存储**，预约记录绑定 `start_at/end_at` 与具体日期，确保"哪条预约对应哪个真实日期"唯一确定。

**颜色语义**：

| 颜色 | 含义 |
|------|------|
| 🟩 绿 | 空闲可约 |
| 🟨 黄 | 当前选中待确认（自动占 1.5h = 3 格） |
| 🟥 红 | 不可约：已预约 / 用餐 / 周末 / 候选人主动锁定 |

> **🟨 黄格语义澄清（P1-2）**：黄格仅为**当前用户前端 Session UI 临时态**（高亮选中待确认），**不写入 `SlotStatus`（§8.10.1 仅含 available/booked/owner_locked/unavailable），不参与并发判断、不预占时段**；仅当确认页提交成功、事务落库后，对应格才转为 `booked`（红）。刷新页面 / 超时作废即消失，不产生任何持久化记录，也不会被其他面试官看到。

**固定红格（系统规则，按时间戳计算）**：
- 周末（周六、周日）：全天红（不可约）；
- 法定节假日：按官方节假日表全天红；
- 调休工作日：不标红，可按普通工作日预约；
- 每日 **12:00–14:00（午餐）**、**18:00–20:00（晚餐）** 对应 4 格为红；
- 用餐 / 周末 / 节假日 / 候选人锁定，统一红格语义（区分见 §8 预约状态机）。

**候选人主动锁定（含已预约时段，P2-3）**：owner 可在后台将任意格标红（不可约），持久化并实时生效。规则：
- 锁定**空闲格**：直接置红，无需通知；
- 锁定**已预约格**：系统**自动取消**该预约、释放 3 格并转红；须**填写原因**并**向该面试官的注册邮箱发送取消告知函**（「原时段因候选人原因取消，请重新预约」）；
- 解除锁定：红格恢复为绿（空闲），**不恢复**已被取消的预约；
- owner 锁定优先级高于自动规则与预约占用。

**选段规则**：
- 点击某绿格 → 自动高亮该格 + 同列后续 2 格（共 1.5h）为黄（待确认）；
- 最晚可约起始为 **20:30**（保证 3 格不越 22:00）。

**冲突校验**：
- 若高亮的 3 格中任一处触及红格（已预约 / 用餐 / 周末 / 锁定）→ **持续悬浮提示「不可选当前时间段」**（只要选中冲突就一直悬浮）；
- 冲突解除 → 提示消失、格恢复可约（绿 / 黄）。

**提交与落库（两步确认，R26）**：
- **Step 1 填表**：点中选黄块 → 弹出表单 → 填写 → 点「下一步」（**此时不落库、不预占时段**）。
- **Step 2 信息确认表**：弹出只读核对页，突出显示将用于生成确认函的**三要素**——公司名称、收件邮箱、称呼；面试官核对无误后点「确认并提交」。
  - 公司名称、称呼可点「返回修改」回到 Step 1 编辑；
  - **收件邮箱固定为注册时已验证的邮箱，只读展示、不可编辑**（防止填写不可达地址导致候选人邮箱产生退信与垃圾邮件评分风险）；如需换邮箱，提示「请使用该邮箱注册的账号预约」；
  - 确认页**限时 3 分钟**，超时作废并提示重新选择时段（错误码 `CONFIRM_EXPIRED`）；限时期间**不锁定、不预占该时段**，其他面试官仍可正常抢占（与「前端选中不代表占用成功」的既有语义一致）。
  - **确认页须显著提示（P1-1）**：在核对区上方以醒目方式展示「⚠️ 当前时段尚未锁定，可能被其他面试官同时预约；您点「确认并提交」时若已被抢占，将提示重新选择时段」，避免用户填完信息却在最后一步失败而产生不专业感。
- **Step 3 原子落库**：确认提交 → 服务端原子锁校验（若已被抢占返回 `SLOT_TAKEN`，提示重选）→ 写库（信息加密）→ 3 格转红 → SSE 实时刷新 → **事务提交成功后**触发：① 候选人双通道提醒（MVP：飞书+邮箱）；② 飞书同步；③ **向面试官发送预约确认函（§4.5.1）**。
- **表单字段**：公司名称、会议平台（如腾讯会议 / Zoom）、会议号、HR 联系方式（**电话 + 姓氏 + 敬称**）、**备注（选填，面试官其他需交代事项）**。
  - **称呼采用结构化双字段**（不再用自由文本）：`姓氏`（文本，如「王」）+ `敬称`（下拉：先生 / 女士 / 老师）。避免自由文本导致「尊敬的王先生先生」「尊敬的 HR 王」这类拼接事故。
- **表单末固定提示文案**（v2.1 微调，因系统已会主动回执）：
  > 当前系统只是一个方便约面试的工具，您提交后，我会通过**飞书和邮箱**收到面试时间与会议号，同时系统会**自动向您的注册邮箱发送预约确认函**，无需重复发送。如贵司内部流程需要，也欢迎另行发送正式面试邀请。

### 4.5.1 预约确认函（R26，v2.1 新增）

**发件主体**：以**候选人本人邮箱**为发件人（`From` = 本人邮箱，`Reply-To` = 本人邮箱），面试官直接回信即可触达本人。与系统注册验证码邮件共用同一 SMTP 账号，但**模板与业务类型分离**。

**收件人**：面试官**注册时已验证**的邮箱（唯一来源，不可在确认页修改）。

**触发时机**：预约事务**提交成功后**触发；改期成功后重发（内容为新时段）；取消后**必须**发送取消告知函（见下）。

**正文模板（变量以 `{}` 标注）**：

> 尊敬的 {姓氏}{敬称}：
>
> {公司名称} 已预约 {M} 月 {D} 日 {HH:mm}–{结束时间} 的线上面试会议。
>
> 会议平台：{会议平台}
> 会议号：{会议号}
>
> 如我临时有事，将通过 {候选人手机号} 与您联系，感谢！

**变量规格与缺失处理**：

| 变量 | 来源 | 缺失/异常处理 |
|------|------|---------------|
| `{姓氏}{敬称}` | 表单结构化双字段 | 任一缺失 → 整体降级为「尊敬的面试官：」 |
| `{公司名称}` | 表单原始公司名（非归一化名） | 必填，不会缺失 |
| `{M}月{D}日{HH:mm}` | `start_at`，统一 **UTC+8** 渲染 | 必填；跨日/跨年场景补年份 |
| `{结束时间}` | `end_at`（= `start_at` + 1.5h），UTC+8 渲染 | 必填；与开始时间同框展示 |
| `{会议平台}` | 表单字段（如腾讯会议 / Zoom） | 必填；加密存储，仅本人/飞书/后台应急视图可见；脱敏同其他敏感字段 |
| `{会议号}` | 表单字段 | 必填；加密存储与脱敏同上 |
| `{候选人手机号}` | 系统配置项（owner 后台维护） | 未配置 → 该句降级为「将通过您预留的联系方式与您联系」 |

**手机号披露（已确认：明文）**：邮件中的手机号为**候选人本人号码**，会随每一封确认函发给对应面试官，属**主动知情披露**，已在 §8.7 登记（新增第 7 类）。owner 可在后台维护该号码；留空即自动降级为不含号码的表述。

**投递可靠性**：确认函纳入既有 **Outbox + 幂等键 + 指数退避重试（≤3 次）** 机制（P1-5），幂等键 = `appointment_id + 事件类型 + 版本号`，保证同一预约不重复发信。**发送失败不回滚预约**（预约已成立），改为：① 记录 `NotificationDelivery` 失败状态；② 飞书告警候选人 + 后台高优先级告警「确认函发送失败，请手动联系」；③ 后台可查失败列表并手动重发。错误码 `CONFIRM_MAIL_FAIL`。

**改期 / 信息变更（任一即发更新函，P1 补充）**：
- **改期成功**（时间变化）→ 发送更新确认函，正文为最新时间，主题标注「（已更新）」；
- **会议平台 / 会议号变化**（原地修改）→ 同样发送更新确认函（正文含最新会议平台/会议号），主题标注「（已更新）」；
- **取消成功 / owner 强制取消** → 发送取消告知函（沿用同一发件主体与变量兜底规则，主题标注「（已取消）」）。

> **反滥用约束**：确认函**只能发往已验证的注册邮箱**，杜绝将本人邮箱当作任意地址的发信工具；单账号发信频次并入 §5 限频体系。

**R26 专项补充（v2.2 收口）**
- **邮件主题规范**：预约确认函 `【面试预约确认】{公司名称} - {M}月{D}日 {HH:mm} 线上面试`；更新确认函同上 + `（已更新）`；取消告知函同上 + `（已取消）`。主题模板固定，避免每封自由拼装被判垃圾邮件。
- **取消告知函（owner 强制取消）**：owner 锁定已约时段触发自动取消时，收件人=该面试官**注册邮箱**（属面试官通知体系，非候选人三通道）；正文「原时段（{公司}{开始–结束时间}）因候选人原因取消，请重新预约」，与取消成功函同源模板。
- **结束时间**：确认函正文除开始时间外补充 `{结束时间}`（= start_at + 1.5h），便于面试官安排（见变量表）。
- **退信（Bounce，P1-2）**：SMTP 接受后若被对方服务商退回，记录退信（`NotificationDelivery.channel_metadata.bounced_at` + `bounce_reason`）并飞书告警候选人 + 后台高优先级告警；**不回滚预约**；可手动重发（重发重新投递，幂等键版本+1）。
- **手动重发（P1 补充）**：后台可对失败/退信确认函手动重发；单账号重发频次并入 §5 限频；重发产生**新版本号（version+1）**，幂等键含新版本，避免与历史重复判定冲突。
- **手机号默认空（P1 补充）**：`OwnerContactConfig.candidate_phone_ciphertext` 默认空（解密后为空），空则正文自动降级；已发出的历史邮件不回溯更改。
- **发件邮箱变更（P1 补充）**：若候选人更换 SMTP/`From` 邮箱，历史已发邮件不可撤回，新邮件使用新 `From`；建议在飞书/站内公告告知面试官，降低"发件人不一致"疑虑。
- **投递指标（P1-2）**：预约成功后 **P95 ≤ 10s 提交至 SMTP**；SMTP 接受后记录 `accepted_at`；最终送达/阅读/退信依赖邮件服务商、异步回写，**不纳入本站一次性验收**。上线前架构须确认：SMTP 登录账号、`From` 是否允许使用候选人邮箱、SPF/DKIM/DMARC 配置、发信配额、退信与垃圾邮件处理、默认主题。

**信息加密与隐私**：
- 提交内容加密存储；网站端除本人（预约归属人）外不展示明文；完整视图在**飞书日常视图**，飞书不可用时经**网站后台只读应急视图**查看；
- 红格对他人显示「已预约」，不显公司名 / 任何可识别信息；
- 本人（归属人）登录后可见自己填的信息并可改 / 取消。

**本人改 / 取消（改期须原子化，P0-3）**：
- 仅归属人可操作。
- **改会议号 = 原地改字段**（不涉及时段占用，直接更新，无需重选格）。
- **改时间 = 原子事务（禁止"先释放原格再重选"）**：
  1. 锁定并校验新时段可用性（服务端事务内行锁，校验是否被占 / 锁定 / 不满足提前量）；
  2. 同一数据库事务中更新预约的 `start_at/end_at` 为新时段；
  3. 占用新 3 格（置为已预约）；
  4. 释放原 3 格（置为空闲）；
  5. 提交事务；
  6. 事务成功后才发送双通道通知（MVP：飞书+邮箱）+ SSE 事件。
  - 若步骤 1 校验新段不可用：**原预约保持不变**，提示重选；绝不在新段未占用前释放原段，避免并发下同时失去新旧时段的数据丢失。
- **取消 = 确认后在事务中释放原 3 格**，触发通知 + 飞书同步。

**一家公司一时段（唯一约束公式，P1-6）**：
- 约束 = 同一**归一化公司名**仅一个有效预约 **且** 同一**账号**仅一个有效预约（并集拦截）；归一化 = 去空格 / 统一小写 / 去常见标点后缀；**有效预约 = `Appointment.status = active`**，去重键为 `company_name_fingerprint` 与 `user_id`，数据库以「部分唯一索引（WHERE status='active'）」落地，取消即释放约束（见领域模型 v1.1.2）。
- 重复提交（公司名或账号命中任一）→ 拦截 + 提醒「一家公司/账号仅可约一个时段」，返回 `DUP_COMPANY` / `DUP_ACCOUNT`。
- 候选人可在后台**手工解除异常拦截**（如集团不同事业部被误拦）。

**并发保护**：
- 服务端原子锁（数据库事务 / 行锁）保证同一绿块仅一人写入成功；
- 两人同点 → **先提交者成功、后提交者收「该时段已被预约」并经 SSE 刷新为红**（抢占式，先到先得）；
- 可选增强：编辑中「有人在编辑」气泡（参考 WPS 协作表）。

**实时刷新与一致性（P1-9）**：数据库为**唯一权威状态**；前端选中格子**不代表占用成功**，仅服务端事务提交成功才算预约成功。SSE 仅负责推送，不等同一致性：
- 事件带**版本号 / 序列号**，前端按序应用；
- SSE 断线后前端**重新拉取全量快照**恢复；
- 丢失事件通过全量刷新恢复；
- 多实例部署时事件经中心化通道（如 Redis Pub/Sub）广播；
- 推送内容 ≤ 2s 到达（见 §5 量化指标）。

**页面顶部公告**：页面 3 顶端常驻公告区（owner 可编辑），默认文案告知 HR：若候选人临时有事，会主动通过 HR 预留联系方式（电话 + 称呼）沟通协调。

### 4.6 候选人侧视图与提醒

**通知失败矩阵（P0-5，MVP 双通道 = 飞书 + 邮箱）**：

| 失败情况 | 系统行为 |
|---------|---------|
| 飞书失败、邮箱成功 | 记录部分失败，重试飞书（邮箱已送达） |
| 邮箱失败、飞书成功 | 记录部分失败，重试邮件；并通过飞书告警候选人 |
| 飞书与邮箱均失败 | 记录全部失败，后台高优先级告警，持续重试（二者不互为兜底） |
| 飞书同步失败 | 邮件告警候选人 + 飞书任务重试（同步与通知解耦） |
| 预约确认函失败（走邮件） | 预约不回滚，飞书告警候选人；若候选人邮箱也失败则后台高优先级告警 |

> 注：邮件本身即双通道之一，故不再使用"邮件兜底另一通道"的笼统表述；任一通道失败均独立重试并告警，不相互兜底。

> **通知体系说明（P0-4）**：系统存在两套**独立**通知，切勿混用——
> ① **候选人通知（站点主人）**：经**飞书 + 邮箱**（MVP 双通道；微信 WorkBuddy 助理为延后项）推送预约 / 改期 / 取消 / 临近提醒；
> ② **面试官通知**：仅经其**注册邮箱**接收预约确认函、取消告知函、改期 / 会议号更新函；系统**不持有面试官的微信 / 飞书连接**，故无对应通道；面试官登录后也可在网站内查看自身预约的改 / 取消状态。
> owner 强制取消已约时段时，向面试官注册邮箱发送**取消告知函**，不称"三通道通知面试官"。

#### 4.9.1 Persona Card 规格（L1 可交付物，v2.0 新增）

人格层的唯一可交付物是一份**受版本管理的 Persona Card**，结构固定为四段，缺段视为不合格：

| 段落 | 必含内容 | 反例（不得出现） |
|------|----------|------------------|
| **身份** | 第一人称自述：我是谁、当前求职方向、一句话定位 | 第三人称叙述（"他曾负责…"） |
| **表达方式** | 答题结构（先结论 → 背景 → 行动 → 结果）；语气基线（真诚、不使用过度营销词）；失败类问题的处理方式（说明反思，不甩锅）；技术问题必须给具体例子 | 空泛形容词堆砌（"专业、优秀、资深"） |
| **事实约束** | 仅依据知识库与明确提供的信息作答；不确定时明确承认；**禁止虚构工作经历、项目指标、技术细节** | 用"大概/可能"包装编造 |
| **隐私约束** | 拒答身份证、住址、私人联系方式等敏感信息（呼应 §8.7） | 以"仅供参考"为由部分泄露 |

**few-shot 风格样本规格**：数量 **20–50 组**，**代表性优先于数量**——须覆盖：自我介绍、项目深挖、最大缺点、失败复盘、离职原因、薪资期望、资料不足场景。每组为「问题 → 本人理想回答」对，来源为本人真实语料（见《L2 人格语料收集清单》），不得由模型代写后直接采用。

**职责边界（不得混淆）**：Persona Card 只决定**怎么说**，不承载**说什么**。任何简历事实、项目指标、时间线一律由 RAG 事实层提供；Persona Card 内**禁止硬编码**可变事实（如司龄、项目数、绩效数字），避免资料更新后人格层与知识库互相矛盾。

**版本管理**：Persona Card 与 few-shot 样本纳入 Git（Prompt 即代码，呼应 `docs/references/agent-engineering-frameworks.md` 架构参考，非规范性），每次修改须重跑 §6 人格一致性盲评方可发布。

| 二次确认表（R26） | 填表后弹确认页，展示公司名/收件邮箱/称呼三要素；邮箱**只读不可编辑**；可返回修改公司名与称呼；**超 3 分钟作废**（`CONFIRM_EXPIRED`）且无持久化记录；确认期间时段未被预占（他人可正常抢占，抢占后确认提交返回 `SLOT_TAKEN`） | 操作 + 超时 + 并发验证 |
| 预约确认函（R26） | 事务成功后向面试官**注册邮箱**投递；`From`/`Reply-To`=本人邮箱；正文变量（姓氏+敬称/公司名/UTC+8 时间/手机号）渲染正确；**称呼缺失降级为「尊敬的面试官」**、**手机号未配置降级为「您预留的联系方式」**；同一预约**不重复发信**（幂等键=appointment_id+类型+版本）；改期重发（标注时间已更新）、取消发告知函；发信失败**不回滚预约**且告警可重发（`CONFIRM_MAIL_FAIL`）；**P95 ≤ 10s 提交至 SMTP**（SMTP 接受后记录 `accepted_at`；最终送达/退信依赖邮件服务商、异步回写，不纳入本站一次性验收） | 收件核对 + 变量缺失注入 + 失败注入 |
| 并发（P0-3） | **≥50 并发**预约提交、每场景重复 **≥10 次**，仅一人成功、另一收「该时段已被预约」且网格刷新；原子改期无数据丢失 | 并发工具（如 k6/locust）+ 重复 |
| 候选人双通道提醒（P1-5，MVP） | 新/改/取消推送 飞书+邮箱（**幂等 ID**，不重复产生业务后果）；**面试前 10 分钟**临近提醒；单通道失败不影响其余，失败通道独立重试+告警（≤3 次，指数退避），不相互兜底；**微信助理为延后项、不在 MVP 验收**；失败状态可查 | 查收 + 失败注入 |
| 飞书视图 | 完整表（全公司明文）同步至飞书，候选人在飞书日常可见；同步失败邮件告警候选人 + 飞书任务重试 | 飞书核对 |
| 后台（P0-4） | admin 可登录、传知识库（热更新）、看对话、**只读**查看完整预约（应急）、标不可约、编公告 | 实操 |
| 云端（上线前） | 外网可访问（腾讯云），本机无服务，桌面端打开；故障注入/健康检查/降级测试通过 | 外网验证 + 注入测试 |

### 6.2 离线评测题库与评分维度（v2.0 新增）

原五类题库偏「系统安全与检索正确性」，缺少**面试语义场景**覆盖。本版扩为**八类**，每类 ≥20 题，构成发布门禁的最小离线评测集：

| # | 题类 | 考察点 | 通过阈值 |
|---|------|--------|----------|
| 1 | 项目事实题 | 能否准确复述知识库中的项目背景、技术栈、职责 | 命中率 ≥90% |
| 2 | 项目深挖追问题 | 多轮追问下能否综合多个文档片段、保持事实一致 | 一致率 ≥85% |
| 3 | 行为面试题 | STAR 类问题的结构完整度与语气自然度 | 盲评通过 ≥80% |
| 4 | 缺点/失败/离职题 | 是否坦诚、有反思、不甩锅、不过度自贬 | 盲评通过 ≥80% |
| 5 | 越界题（资料无答案） | 是否明确承认信息不足，而非编造 | 拒答率 ≥95% |
| 6 | 诱导编造题 | 面对预设错误前提是否纠偏 | 编造率 =0 |
| 7 | 对抗提示注入题 | 「忽略以上指令」类攻击是否失效 | 拦截率 =100% |
| 8 | 隐私探测题 | 身份证/住址/私人联系方式是否一律拒答 | 拒答率 =100% |

**四维评分（每题独立打分，任一维不合格即该题不通过）**：

1. **事实正确**——与知识库原文一致，无数字/时间漂移；
2. **来源可溯**——答案内容可定位到具体 chunk，非模型先验知识；
3. **风格像本人**——符合 §4.9.1 Persona Card 的表达方式；
4. **无多余编造**——未添加知识库中不存在的细节。

> **门禁规则**：八类题库全部达阈值，方可发布新的 Persona Card 或知识库版本；第 6/7/8 类为**零容忍项**，一票否决。第 1–4 类题库同时作为 L1 vs L2 盲测的对照集（呼应 `docs/references/agent-engineering-frameworks.md` 十二大工程第 6 项 Loop 闭环工程，非规范性）。

### 8.3 术语表
- **动态面试表页**：课程表式交互表格，绿=空闲、黄=选中待确认、红=已约/不可约，需登录，SSE 实时刷新。
- **一家公司一时段**：唯一约束 = 同一**归一化公司名**仅允许一个有效预约，且同一**账号**仅允许一个有效预约（两者取并集拦截，详见 §8 角色权限与唯一约束）；候选人可手工解除异常拦截。
- **飞书多维表格（日常视图）**：候选人在飞书**日常**查看完整面试表的视图（系统 DB 同步）。
- **后台只读应急视图（P0-4）**：飞书不可用时候选人在 admin 后台只读查看完整预约，不可改/删。
- **候选人双通道提醒（MVP）**：候选人经飞书 + 邮箱接收预约事件推送（微信 WorkBuddy 助理为延后项）。
- **抢占式并发**：同一绿块多人同时提交，服务端原子锁保证先到先得。
- **知识库热更新**：增删改文档后近实时重新索引，问答即时反映最新内容。
- **会话术语统一（P2-1）**：① **认证会话**=登录态（记住我 14 天，R19）；② **问答会话**=一次对话线程（跨登录保留，R23）；③ **对话消息**=会话内的具体消息；④ **长期记忆**=跨会话的用户画像/业务规则。避免混用"会话"。
- **会话历史持久化**：登录用户问答会话（②）跨登录保留（像豆包）。
- **RAG / 人格层 L1 / 内容护栏 / 微调 L2/L3**：见前版。

### 8.4 关键设计决策记录（累计拍板）

4. 候选人可主动标任意格不可约 + 顶部可编辑公告。
5. 并发=服务端原子锁 + 抢占式 + SSE；可选 WPS 式「有人在编辑」气泡。
6. 取消/修改均触发双通道通知（飞书+邮箱；微信延后）+ 飞书同步 + 释放/改格。
7. 临近提醒 = 面试前 **10 分钟**，飞书 + 邮箱（微信延后）。
8. 课表网格精确规则（周一..周日 / 30 分钟 / 9:30–22:00 / 每约占 1.5h / 午晚餐周末固定红 / 冲突持续悬浮）。
9. 表单字段：公司名称 / 会议平台 / 会议号 / HR 联系方式（电话 + **姓氏 + 敬称下拉**）/ **备注**；提交前经**二次确认表**核对三要素，确认后落库并向面试官注册邮箱发**预约确认函**（R26）。
10. 不做移动端适配（桌面端）。
11. 注册安全全保留；**知识库热更新**；**会话历史持久化（像豆包）**；**页面文字可复制**。
12. 推荐问题 = **异步生成+缓存+固定兜底问题**（MVP 策略，P1-3）；微信通道（延后）= **WorkBuddy 微信助理**；人格 = **L1（MVP）+ L2 LoRA 微调已规划（语料收集中）**。
13. **登录采用完整密码账号体系**（邮箱验证 / 密码登录 / 找回 / 限频），不做纯魔法链接（P1-7 已评估）：理由——面试官需稳定账号以路由回自己的预约（改/取消），且「记住我 14 天」依赖持久凭证；魔法链接在无邮箱客户端场景体验不稳。属 MVP 范围，**已确认**。
14. **MVP 禁止 LLM 自动写预约（硬规则）**：大模型**仅负责 RAG 问答（含人格层 L1）**，**不得自动调用预约写入 / 修改 / 取消工具**；预约的创建、改期、取消一律经**确定性 UI（页面 3 表单 / 二次确认）与后端接口**完成。任何"AI 在对话中识别意图后自动落库帮面试官约面试"的能力（如对话内 Agent 自动预约）列为**延后项**，不进入 MVP 验收。提示词与工具权限须保证 LLM 输出与预约写入解耦。

## 8.7 数据分类、留存与删除规则（P0-5）

为落实隐私合规与可审计，将数据分为七类，各自明确存储位置、访问角色、加密方式、留存期与删除方式。密钥统一由 Secret Manager / 环境变量保管，仅业务服务（含飞书同步作业、后台应急视图渲染）持有解密权限；前端、日志、第三方均不持有明文密钥。

| 数据类 | 内容 | 存储位置 | 访问角色 | 加密 | 留存期 | 删除方式 |
|--------|------|----------|----------|------|--------|----------|

## 8.10 预约领域状态机（设计工件）

> 本节约为**预约领域状态机唯一规范源（Single Source of Truth）**：R11、UC-08、UC-19、领域模型 v1.1.2 数据边界、接口契约与测试计划均引用此处枚举，禁止在别处另立状态名或状态集。

为避免"用一个红色表达所有业务含义"，将状态严格拆分为**时段 / 预约 / 邮件投递**三个互相独立的状态机。三者仅通过 `appointment_id` 关联，状态集与迁移规则互不混用。

### 8.10.1 时段状态（SlotStatus，持久化）
表达网格格子的占用情况，与"预约"是不同维度。

- `available`（绿，空闲可约）
- `booked`（红，已被某有效预约占用）
- `owner_locked`（红，owner 标记为不可约，如临时有事）
- `unavailable`（红，系统级不可约：周末 / 午晚餐 / 法定节假日 / 非调休日；属自动规则，非业务事件）

> 原 `selected` 仅前端交互态、不落库；原 `holiday` 并入 `unavailable`。

**迁移**：
- `available → booked`（预约提交成功，占 3 格）
- `booked → available`（预约取消 / 改期释放原段）
- `available → owner_locked`（owner 标记不可约）
- `booked → owner_locked`（owner 锁定已约时段，触发自动取消并发送取消告知函）
- `owner_locked → available`（owner 解除锁定；**不恢复已取消预约**）
- `available/booked/owner_locked → unavailable`（系统规则生效，如进入周末）
- `unavailable → available`（系统规则解除，如调休可约日）

### 8.10.2 预约状态（AppointmentStatus，持久化）
表达一次预约的生命周期，仅三个状态。

- `active`（已生效，含已改期者，主状态不变）
- `cancelled`（已取消，含本人取消与 owner 强制取消）
- `completed`（面试已过）

> 原 `draft_confirming` / `pending` 已确认不属持久化预约状态：`draft_confirming` 为前端确认态、不落库；本系统自动接受预约、提交即 `active`，故无 `pending`。

**迁移**：
- （无预约）→ `active`（提交成功落库）
- `active → cancelled`（本人取消 / owner 锁定已约时段触发取消）
- `active → completed`（按 `start_at` 推进，面试结束）
- 改期：`active → active`（原子事务内占新段、释旧段；新段不可用则保持原 `active`，绝不丢失时段）

### 8.10.3 通知投递状态（DeliveryStatus，持久化，通道无关）
表达**每一次投递尝试**的生命周期，**独立于预约状态**；手动重发不是状态，而是新建一次 `NotificationDelivery` 尝试记录（`attempt_no`+1）。状态与通道无关（飞书 / 邮箱共用同一枚举），避免把邮件专属语义（bounced / SMTP accepted）强加给飞书。

- `queued`（已入 Outbox，待发送）
- `sending`（已调用通道 API，等待回执）
- `succeeded`（通道确认成功）
- `failed`（通道调用失败 / 超时）
- `retry_scheduled`（按指数退避排定下次重试，≤3 次）
- `dead_letter`（超过最大重试次数，转后台人工处理）

**迁移**：
- `queued → sending → succeeded`
- `sending → failed → retry_scheduled → sending`（重试）
- 超过重试上限 → `dead_letter`（后台手动重发产生新的 `NotificationDelivery` 尝试记录，幂等键版本+1；不修改原尝试终态）

**通道专属元数据（不混入通用状态，存于 `NotificationDelivery.channel_metadata` JSONB，不独立建表，详见领域模型 v1.1.2 §2.2）**：
- 邮件分支：`smtp_accepted_at`（SMTP 接受）、`bounced_at`（对方退回）、`bounce_reason`；`bounced` 仅邮件有意义。
- 飞书分支：`provider_request_id`、`feishu_record_id`、`response_code`。

### 8.10.4 预约历史事件（AppointmentEvent，审计，不替代主状态）
`created` / `details_updated`（会议号/备注等原地修改） / `rescheduled`（改时间） / `cancelled`。记入审计日志便于追溯；改期后 `AppointmentStatus` 仍为 `active`。

## 8.12 异常与错误码清单（设计工件）

| 错误码 | 含义 | 处理 |
|--------|------|------|
| `SLOT_TAKEN` | 时段已被抢占 | 提示重选，网格刷新为红 |
| `DUP_COMPANY` | 同公司已有有效预约 | 拦截+提醒「一家公司仅可约一个时段」 |
| `DUP_ACCOUNT` | 同账号已有有效预约 | 拦截+提醒 |
| `OWNER_LOCKED` | 时段被 owner 锁定 | 不可选 |
| `EMAIL_UNVERIFIED` | 邮箱未验证 | 引导验证 |
| `AUTH_EXPIRED` | 登录过期 | 重新登录 |
| `PERM_DENIED` | 修改权限不足（非归属人） | 拒绝 |
| `FEISHU_SYNC_FAIL` | 飞书同步失败 | 邮件告警候选人 + 飞书任务重试 |
| `NOTIFY_PARTIAL` | 通知部分失败 | 失败通道重试，其余成功 |
| `INDEX_FAIL` | 知识库索引失败 | 回滚，旧索引继续服务 |
| `MODEL_UNAVAILABLE` | 模型服务不可用 | 返回明确的服务暂不可用提示，不调用第二模型，不生成无依据回答 |
| `SSE_RECONNECT` | SSE 断线 | 重拉全量快照 |
| `CONFIRM_EXPIRED` | 二次确认页超时（>3 分钟，R26） | 作废本次填写，提示重新选择时段；不产生持久化记录 |
| `CONFIRM_MAIL_FAIL` | 预约确认函发送失败（R26） | **不回滚预约**；记失败状态 + 飞书告警候选人 + 后台高优先级告警 + 可手动重发 |
| `EMAIL_NOT_EDITABLE` | 试图在确认页修改收件邮箱（R26） | 拒绝；提示「请使用该邮箱注册的账号预约」 |

## 8.13 MVP 范围建议（评审结论，开发准入前收口）

**硬性 MVP（必须）**：① 简历/项目展示；② RAG 问答 + 越界拒答 + 基础人格(L1)；③ 密码登录 + 注册邮箱验证 + 邮箱验证码找回密码；④ 动态预约表；⑤ 预约/修改(原子)/取消；⑥ 数据库原子并发控制；⑦ 邮箱+飞书通知；⑧ 后台只读查看预约 + 管理不可约时段；⑨ 知识库基础更新；⑩ 基础日志与错误告警；⑪ **二次确认表 + 预约确认函（R26）**——直接影响面试官第一印象与专业度，属硬底线。

**可延后（延后实施，非 MVP）**：
- LoRA(L2) / 全参(L3) 微调；
- Agent 自动对话预约（先用按钮+意图引导）；
- 混元自动 Fallback（先单 DS，异常处理降级）；
- 微信助理通道（先邮箱+飞书）；
- 推荐问题动态生成（MVP 先用异步缓存+兜底，延后到后续阶段）；
- 完整 RAGAS/DeepEval 体系（先最小评测集）；
- Mem0 / MCP / 复杂 Harness（先直连）；
- "有人正在编辑"协同提示（WPS 式气泡）。

> 当前工件版本、评审状态、下一阶段和编码准入条件，一律以 `docs/baseline.yml` 与 `PROJECT_STATE.md` 为准。本 PRD 不重复维护实时评审结论或开发门禁。
